# AI 面试陪练：AI 工作流

## 1. 总体架构

MVP 不使用单个大 Prompt 完成全部任务，而是拆成 6 个独立节点：

```text
简历解析
  → JD 解析
  → 证据匹配
  → 问题生成
  → 回答诊断与动态追问
  → 评分与综合报告
```

每个节点使用结构化输入输出，并通过 Schema 校验，避免上游错误静默传递到下游。

## 2. 节点一：简历解析

### 输入

- PDF 提取文本或用户粘贴文本。

### 输出字段

```json
{
  "education": [],
  "experiences": [
    {
      "id": "exp_01",
      "organization": "",
      "project": "",
      "context": "",
      "actions": [],
      "metrics": [],
      "outcomes": [],
      "skills": [],
      "uncertainties": []
    }
  ],
  "ai_related_evidence": [],
  "claims_requiring_verification": []
}
```

### 规则

- 只提取文本中真实存在的信息。
- “参与”“协助”“负责”“独立负责”必须原样区分。
- 指标需保留原始口径；口径未知时标记为未知。
- 不得根据职位名称推断用户实际职责。

## 3. 节点二：JD 解析

### 输出字段

```json
{
  "role": "AI产品经理实习生",
  "responsibilities": [],
  "competencies": [
    {
      "name": "AI生成质量评估",
      "importance": 5,
      "jd_evidence": "协助建立AI生成内容的质量评估标准",
      "expected_evidence": []
    }
  ],
  "requirements": [],
  "bonus_items": []
}
```

### 首个基准 JD 能力

- AI 生成入口与完整用户链路；
- 多模态输入与失败处理；
- 需求文档、流程图和交互说明；
- 用户行为漏斗分析；
- 竞品调研和可用性测试；
- 需求评审、测试、上线和复盘；
- AI 生成质量评估。

## 4. 节点三：证据匹配

为每项 JD 能力匹配简历证据，并划分强度：

- `strong`：有具体场景、个人行动和结果；
- `medium`：有相关经历，但结果或个人贡献不完整；
- `weak`：只有概括性表述，无法讲出具体案例；
- `missing`：没有对应证据。

```json
{
  "competency": "用户研究",
  "match_level": "medium",
  "resume_evidence_ids": ["exp_02"],
  "strength_reason": "有访谈和需求总结经历",
  "evidence_gaps": ["缺少研究如何影响产品决策的证据"],
  "interview_risk": "medium"
}
```

## 5. 节点四：问题生成

### 问题配比

1. 简历证据核验题 × 2；
2. JD 能力匹配题 × 2；
3. 场景迁移/模糊需求拆解题 × 1。

### 输出结构

```json
{
  "question_id": "q_01",
  "question": "",
  "question_type": "resume_verification",
  "source_evidence": [],
  "competencies": [],
  "reason": "",
  "expected_evidence": [],
  "max_follow_ups": 2
}
```

### 约束

- 至少 2 道题必须引用简历中的具体项目、数字或表述。
- JD 题必须与目标岗位职责直接相关。
- 不得生成只靠背诵概念即可作答的问题。
- 问题应能区分“知道概念”和“真正做过”。

## 6. 节点五：回答诊断与动态追问

### 诊断维度

```json
{
  "evidence_status": {
    "context": true,
    "personal_role": false,
    "action": true,
    "decision_reason": false,
    "data_or_observation": true,
    "outcome": false,
    "validation": false,
    "limitations": false
  },
  "strongest_evidence": [],
  "main_gap": "",
  "credibility_risk": "low",
  "follow_up_needed": true,
  "follow_up_question": ""
}
```

### 追问路由

| 缺口 | 推荐追问 |
|---|---|
| 场景不清楚 | 当时的具体背景、目标和限制是什么？ |
| 个人角色不清楚 | 哪些部分由你负责，哪些由其他人完成？ |
| 缺少决策依据 | 为什么选择这个方案，而不是其他方案？ |
| 缺少数据 | 你根据哪些样本、指标或用户反馈得出结论？ |
| 缺少结果 | 方案是否采用或上线？你能确认的结果是什么？ |
| 未实际落地 | 如果重新做，你会如何设计验证？ |
| 结论超出证据 | 现有数据能直接证明这个结论吗？哪些只是推断？ |
| 无法回答 | 标记证据不足，并建议弱化简历表述或补充项目。 |

### 停止条件

满足任一条件则停止追问：

- 主要证据点已经完整；
- 已追问 2 次；
- 用户明确说明不知道或没有参与；
- 下一次追问只会诱导用户猜测或虚构；
- 用户回答与岗位能力无关，应结束该题并记录缺口。

## 7. 节点六：评分与报告

评分器只能使用：

- 已确认的简历信息；
- 用户在本次面试中的回答；
- 当前 JD 的明确要求；
- 预先定义的 Rubric。

禁止：

- 根据常识补全项目结果；
- 把“计划验证”写成“已经验证”；
- 把团队成果全部归给用户；
- 用语言流畅度掩盖证据不足；
- 因用户坦诚未知而自动判断其不可信。

## 8. 报告输出结构

```json
{
  "overall_summary": "",
  "overall_score": 0,
  "dimension_scores": [],
  "strongest_evidence": [],
  "evidence_gaps": [],
  "resume_risks": [],
  "question_reviews": [],
  "next_training_tasks": [],
  "disclaimer": "本报告用于面试训练，不代表真实招聘结论。"
}
```

## 9. 系统级安全检查

最终输出前执行独立检查：

1. 报告中的项目、数字、角色能否在输入中找到来源；
2. 是否把假设写成事实；
3. 是否新增用户没有提供的落地结果；
4. 分数与评分理由是否一致；
5. 引用证据是否真正支持对应判断；
6. 是否包含简历中的联系方式等不必要隐私信息。
